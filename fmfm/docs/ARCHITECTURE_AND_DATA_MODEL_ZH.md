# FMFM：面向去中心化市场的资金流基础模型

## 目标

FMFM 不以“预测一条看起来漂亮的未来 K 线”为终点，而是学习公开市场事件的时序结构，输出可检验的概率预测，再通过成本与风险约束形成交易决策。

核心原则：**资金流是主线，K 线是市场事件的聚合视图，交易收益是最终验收标准。** 不使用情绪/舆情作为模型输入。

## 1. 数据观：不是所有资产都有一份统一的“链上账本”

不同市场的公开数据结构不同，必须按市场类型接入，不能把它们假装成同一种账本：

- **链上现货 DEX**：区块、交易、Swap 事件、池子储备/流动性变化、代币转账、铸造/销毁、池地址与代币元数据。交易事件可重建池级成交序列，但不是每个代币都有单一、完整、可信的“资产总账”；同一资产可能在多个链、池和桥之间流通。
- **链上订单簿/永续合约**：链上交易/清算/资金费率等可见事件，加上交易平台公开的订单簿、成交、标记价/指数价、资金费率 API。公开 API 不等于完整历史账本，也不一定公开所有订单生命周期。
- **中心化交易所**：公开成交、K 线、盘口、资金费率、持仓量等 API；这部分不是链上账本，需单独标记来源和可信度。
- **跨市场资产映射**：必须维护 chain_id、token_address、pool/market_id、quote asset、合约类型、价格单位、精度、时间戳和数据来源，不能只靠 symbol 合并资产。

## 2. 数据分层

### A. 原始事件层（不可覆盖）

保留原始响应/事件及采集元数据：source、chain、market、asset、event_time、ingest_time、block_number、tx_hash、log_index、sequence_id、payload、schema_version。按事件 ID 去重；链上数据还需处理重组/确认数，WebSocket 断线后补拉缺口。

### B. 标准化事件层

把原始数据转成统一但不抹平差异的事件模型：
- trade/swap：价格、数量、计价金额、主动买卖方向（仅在来源定义可验证时）、手续费；
- book：买卖盘价量、价差、深度、盘口不平衡；
- liquidity：增加/移除、储备变化、池深度；
- perp：funding、open interest（若可用）、清算、标记价/指数价；
- chain：区块高度、确认状态、交易成本、事件顺序。

缺失字段保留为缺失值，不能将推断值伪装成真实观测。链上地址可用于聚合资金流，但不能未经验证就给地址贴“聪明钱”等标签。

### C. 时间窗特征层

按事件时间聚合为 1s/1m/5m/15m/1h 等窗口，并保留原始事件链接：
- 真实成交买卖不平衡、净主动成交额、成交强度、成交额变化；
- 盘口价差、各档深度、订单簿不平衡（仅对有订单簿市场）；
- 池子储备/流动性变化、Swap 价格冲击、成交量/流动性比（DEX）；
- funding、OI 变化、清算方向/规模（永续合约且数据可得时）；
- OHLCV 作为聚合视图，而不是唯一输入；
- 跨市场价格差、成交流方向差、链上与场内价差（需统一时间与计价币）。

### D. 预测与决策层

建议分成多任务输出，而不是只回归未来 close：
1. 未来收益分布/分位数，而非单点价格；
2. 未来波动率与区间；
3. 未来成交/净资金流方向和强度；
4. 多个持有期的方向概率；
5. 达到止盈/止损的概率、最大有利/不利波动估计；
6. 数据质量/模型不确定性与“不交易”概率。

然后由独立决策器计算期望净收益：预测收益减手续费、滑点、资金费率、Gas/路由成本；只有净优势超过门槛且风险预算允许才生成交易计划。

## 3. 与 Kronos 的关系

Kronos 的核心是把 K 线数值序列编码为离散 token，再用自回归目标学习金融时间序列。FMFM 可以借鉴：
- 连续行情/成交特征的分词或分桶；
- 自回归序列预训练；
- 多市场、多资产共享表示；
- 用预测下一段序列作为预训练任务。

但不能把原始链上事件简单转成 K 线后就宣称有创新。FMFM 的差异应是**事件级资金流表示 + 市场微结构/链上状态 + 多任务预测 + 交易成本感知决策**。可先做小型可验证基线，再比较 Kronos、LightGBM、TCN/Transformer 等方案，避免先假设复杂模型一定更好。

## 4. 预测未来 K 线，为什么不等于能赚钱？

一条生成的 K 线是模型条件概率下的一种可能路径，不是未来事实。模型应生成分布/多个情景或分位数，并报告校准误差。即使方向判断正确，仍可能因为：
- 预测幅度小于手续费与滑点；
- 先触发止损、后到达目标；
- 盘口深度不足，无法按显示价格成交；
- 永续合约资金费率、强平和杠杆放大损失；
- 数据泄漏、时间戳错位、过拟合或市场状态变化；
而产生亏损。

因此验收顺序应是：时间外预测质量 → 扣成本回测 → walk-forward → 纸面交易 → 小额受控上线，而非先看生成的 K 线是否“像真的”。

## 5. 研究路线

1. **数据验证**：先选 Hyperliquid 的 BTC/ETH/SOL 永续市场；历史 candle、盘口快照、公开成交/资金费率可用范围逐项核验。不要假设公开 API 能提供完整历史订单簿。
2. **基线**：OHLCV-only、真实成交流、盘口特征、资金费率/OI 特征逐步做消融对比。
3. **标签**：多个 horizon 的未来收益、波动率、止盈/止损先后触达；标签只用于训练目标，不得进入同一时点的输入特征。
4. **模型**：先训练简单模型建立可复现基线，再试 Kronos 式 tokenizer/autoregressive 模型与事件序列编码器。
5. **评估**：严格按时间切分、walk-forward、跨资产测试；计入手续费、滑点、funding、延迟与成交限制；报告 Sharpe、最大回撤、换手率、净收益、置信区间及基线对照。
6. **上线**：先只读监控与纸面交易；交易签名/私钥与研究模型隔离。模型不得持有或输出私钥，执行层有独立限仓、熔断、最大亏损和人工停机机制。

## 6. 第一阶段明确不做

- 不把情绪、社交媒体、新闻作为输入；
- 不宣称能准确知道未来价格；
- 不用未验证的地址标签作为“资金聪明度”；
- 不在回测未通过前自动实盘；
- 不把不同链、不同池、不同合约的同名资产直接合并。
